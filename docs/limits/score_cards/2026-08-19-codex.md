# Repository scorecard

**Assessment date:** 2026-08-19  
**Scope:** repository state at `origin/main` (`dee30807`) after the D13/D14
investigation and Sim-Short heartbeat continuation.  
**Purpose:** a durable engineering baseline for release planning. This is a
repository-capability assessment, **not** an `L*` measurement-instrument limit.
The measured apparatus limits remain indexed in [the limits ledger](../README.md).

The grades are deliberately demanding. An `A` means the repository's claims are
supported by repeatable evidence and the normal workflow enforces the claimed
standard. A `C` means the capability exists but important paths are unreliable or
only partially enforced. A `D` means written intent and routine practice materially
diverge.

## Summary

| Area | Grade | Short reason |
|---|---:|---|
| Research integrity | **A** | Negative results, preregistration, provenance, retractions, and claim scope are unusually explicit. |
| Ambition and originality | **A** | The substrate-primary, embodied-learning, and multi-layer memory work is substantial and genuinely distinctive. |
| Documentation honesty | **A-** | Individual investigations are candid; navigation and status synchronization lag the volume of material. |
| Runtime correctness | **C-** | Core paths work, but confirmed silent contract failures and planning liveness defects remain. |
| Maintainability | **D+** | Giant cyclic control-plane functions and exception-heavy seams make local reasoning unreliable. |
| Test quantity | **A** | The repository has a very large, detailed unit, integration, behavioral, and experiment test corpus. |
| Test/CI truthfulness | **C** | CI covers only a subset of the advertised fast suite; supposedly offline tests can use the network or user home. |
| Release governance | **D** | Version policy, changelog/release state, active-plan status, and actual merge state disagree. |
| Near-term potential | **High** | The corrective direction is clear and most weaknesses are consolidation work, not a need for a rewrite. |

## Why each grade was earned

### Research integrity — A

Strengths:

- behavioral claims carry evidence, caveats, and re-run triggers;
- negative or void results are retained instead of rewritten as wins;
- instrumentation limits are characterized separately from defects;
- hardware failures and contaminated measurements are documented explicitly;
- biological mappings increasingly distinguish functional analogy from mechanism.

To keep the grade: preserve the current evidence discipline while reducing the
number of manually synchronized ledgers. The danger is not dishonesty; it is that
truth becomes too expensive to retrieve.

### Ambition and originality — A

Maxim is not a thin orchestration wrapper. It contains a serious attempt at
substrate-primary action selection, embodied feedback, persistent associative
memory, causal credit, simulation apparatus, hardware execution, and cross-instance
state exchange.

To keep the grade: do not let novelty become the release criterion. Through 1.1,
the project should prefer making an existing mechanism executable and observable
over adding another mechanism name.

### Documentation honesty — A-

The bug, limit, experiment, and graduation ledgers are unusually candid. The minus
reflects information architecture rather than prose quality:

- about 50 plan documents remain at the active root despite the stated
  root-means-active rule;
- completed plans still say `DRAFT` or `not started`;
- the superseded 1.1 checklist still assigned Oasis to 1.1;
- `ARCHITECTURE.md`, `DECISIONS.md`, API counts, Python support, and dependency
  descriptions have drifted;
- provider-specific private-memory links remain in tracked documents.

Upgrade condition: one authoritative release ledger, provider-neutral tracked
review procedures, and automated checks for status/link/instruction drift.

### Runtime correctness — C-

Confirmed defects include:

- a failed planning turn can be dropped and leave the simulation live but idle
  (D13), while the spinner asserts nonexistent work (D14);
- stable `maxim.run()` inputs are accepted without delivering their documented
  behavior (`goal`, `robot`, and partially `home_dir`);
- `maxim.load.agent()` does not immediately restore every subsystem it promises;
- custom tool registration is consumed once despite documentation implying a
  persistent registration;
- some central learning/event paths are wired but functionally inert (D6/D9).

Upgrade to `B-`: close D13/D14 and the stable-API contract set with black-box tests,
make lifecycle cleanup structural, and require every public argument to have an
observable effect or an explicit rejection.

### Maintainability — D+

The project is modular by file count but still behaves like a cyclic control-plane
monolith. At the assessment point:

- `run_agentic_loop` was approximately 3,331 lines;
- `start_simulation_mode` was approximately 3,226 lines;
- CLI `_main_impl` was approximately 1,737 lines;
- the shipped architecture audit reported 32 violations at the assessment
  snapshot (33 on current `main` after the D22 merge);
- synchronous persistence and broad fail-soft handling remain in control-loop
  paths.

Upgrade to `C+`: finish fail-loud measurement work, establish an accepted-debt
architecture baseline, then extract lifecycle-owned phases at observed failure
seams. A broad rewrite would increase risk; this must be incremental and guarded.

### Test quantity — A

The repository has hundreds of test files and thousands of collected tests,
including valuable contract, architecture, hardware-safety, experimental, and
regression guards. This is a real asset.

To keep the grade: retain narrow, evidence-linked tests while pruning tests that
only pin accidental divergence rather than desired behavior.

### Test/CI truthfulness — C

Direct verification found that:

- CI runs `tests/unit/`, not the broader fast-suite command required by the agent
  instructions;
- the unit suite becomes network-dependent when `sentence_transformers` is
  installed but the model is not cached;
- a behavioral mock test writes under `~/.maxim` through its subprocess harness;
- a substrate test and model-backed unit test may contact Hugging Face;
- teardown can attempt to persist cost state under the user's home directory;
- the architecture test asserts only that auditing returns a list, while the real
  audit exited nonzero with 32 findings at the assessment snapshot (33 on the
  current post-D22 merge candidate).

Upgrade to `B`: make the required fast suite hermetic with a temporary data home,
mark model/network tests explicitly, add one risk-based integration/substrate CI
job, and reject architecture violations above a reviewed baseline.

### Release governance — D

At assessment time the package remained `1.0.6` after roughly 60 post-tag commits,
including 27 source-changing commits, despite instructions requiring runtime/API
changes to bump the version. The changelog covers only part of that work; GitHub
release state and tags are not fully aligned; plan status has drifted from merge
state.

Upgrade to `B-`: choose a realistic versioning policy, maintain one 1.1 release
checklist, reconstruct the unreleased change record, and publish Git tag, GitHub
release, changelog, package version, and PyPI artifact as one release transaction.

changes. A grade should move only when normal tests, CI, or release procedure now
enforce the improvement—not merely because a plan exists.
