- **[engineering] Reachy head pose is WORLD-frame and sits ABOVE `body_yaw` — `goto_target(body_yaw=X)` with `head=None` COUNTER-ROTATES the head, so head-mounted sensors DO NOT turn with the body** (2026-07-16; cost a full session and six wrong hypotheses). Pollen's [AGENTS.md](https://github.com/pollen-robotics/reachy_mini/blob/main/AGENTS.md), verbatim: *"The head matrix is in world frame, so `body_yaw` alone pivots the body under the head — to make the head follow the body, ship a `head` matrix in the same call with the body delta added to the head yaw."* Their daemon confirms the mechanism (`backend/abstract.py::update_target_head_joints_from_ik`: `if pose is None: pose = self.target_head_pose` → `ik(pose, body_yaw=body_yaw)`) — **`head=None` means "re-solve IK against the RETAINED world head target", NOT "leave the head alone"**; the Stewart platform actively counter-rotates to hold the head's absolute orientation. **The microphone array and camera live in the HEAD.** Measured: a 0.9 rad body command rotated the mics only 0.32 rad (`d(head)/d(body)` = **+0.214** in world frame; **+1.012** after the fix). This manufactured a phantom *"the XVF3800 DoA is a slow tracking estimator that loses lock on large jumps"* pathology that survived six hypotheses (settle lag, backlash, under-travel, speech density, increment size, slow adaptation) and was written into three docs as a finding before Pollen's own documentation settled it — DoA gain went 0.19-0.39 (wild, irreproducible) → **0.562 stable, converging in 0.23 s** the moment the head was commanded to ride along. **Rule: any code that turns the body and then reads a head-mounted sensor MUST ship an explicit `head=` matrix with the body delta added to head yaw** (`create_head_pose(yaw=degrees(body_yaw))` gives a rigid head-follows-body; head yaw reads ±180° precisely because `body_yaw` supplies most of it — the platform's own ~±15-18° is not the constraint). Also call `set_automatic_body_yaw(False)` when your loop owns the yaw axis, or the daemon may modulate commanded `body_yaw` behind you. **Generalized lesson (the expensive part): when a measurement disagrees with the model, verify the ACTUATION assumption — did the thing you are sensing with actually move? — BEFORE theorizing about the sensor; and read the vendor's docs before reverse-engineering their kinematics.** **The shipped path was ALSO broken until 2026-07-16** — `ReachyMiniController.goto_target` passed `head=None` for body-only moves and composed head yaw as if body-relative when it is world; a post-merge review caught it after the invariant was already written (the fix had landed only in `scripts/`). Regression guard: [tests/unit/test_reachy_head_frame.py](tests/unit/test_reachy_head_frame.py) — 5 offline tests against a fake SDK pinning the production `ReachyMiniController` path (body-only ships a head matrix; head world-yaw tracks body; `head_yaw` is body-relative and composed onto the body; a head-only command composes against the body's angle — since the 2026-08-09 F1 fold that is the last COMMANDED body once one exists, with the readback as the one-shot seed (see the retained-axes invariant below); `get_current_pose()` exposes `body_yaw`). **Verified to fail 5/5 on the pre-fix controller.** (An earlier version of this line cited `scripts/orient_backbone/live_common.py` + `yaw_verify.py` — neither is a valid guard under Principle 5: the former is a research script nothing imports and it demonstrably did NOT enforce the rule for `src/maxim/`; the latter needs a robot on the LAN and can never run in CI. `yaw_verify.py` remains the *hardware calibration* step, not the guard.)
