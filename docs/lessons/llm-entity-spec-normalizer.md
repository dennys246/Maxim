- **[engineering] LLM-derived entity specs route through `normalize_llm_entity_spec` before `_parse_entity`** (v1 C4-followup-1, 2026-05-29). C4 (`v1_refinement.md` §C4) requires every modulator to either own ≥1 sensor or declare `abstract: true`. **Post-PR-A.3 (C4 hard-error flip, 2026-05-29) this normalizer is LOAD-BEARING**: without it, every LLM-imagined or foundry-generated entity with a bare capability-only modulator crashes `_parse_entity` with `ConfigurationError`. Bundled YAMLs are audited; user-authored YAMLs (DM campaigns via `campaign_runner`, curated arc data via `generative_runner`) get the 1.0 `ConfigurationError` as the **user-facing migration signal** asking the author to add the marker explicitly. LLM specs (`imagination/trigger.py` 3 sites + `simulation/foundry.py` 2 sites) cannot be expected to remember the marker — the normalizer is the safety net that fills `abstract: True` on capability-only modulators. Per-source contract is deliberate: do NOT auto-normalize bundled / user YAMLs (that would suppress the user-migration signal). The LLM prompt in [`simulation/entity_designer.py::_SEM_SCHEMA_PROMPT`](src/maxim/simulation/entity_designer.py) is the right-shaped ask; the normalizer is the post-process backstop for LLM forgetfulness. Regression guard: CI grep in [.github/workflows/test.yml](.github/workflows/test.yml) ("v1 C4-followup-1 LLM-spec normalizer rule") allow-lists the four non-LLM input source files (`embodiment/spec.py` internal, `embodiment/component_registry.py` bundled, `simulation/campaign_runner.py` user YAML, `simulation/generative_runner.py` curated arc) and rejects any new `_parse_entity(` caller outside them that omits the normalizer — new LLM-derived entry points must update both the allow-list and this invariant in the same commit; new non-LLM bundled/user-YAML sources also update the allow-list to extend the migration-signal coverage.
