**[engineering] `config.json::llm.profile` vs `active_llm_model.{role}.txt` are intentionally separate state files** (2026-06-09 footgun surfaced via the Exp 37 Mistral24B kickoff). `config.json` is the **declarative** operator-intent layer (per [config_unification.md C2](docs/plans/archive/config_unification.md)); `active_llm_model.{role}.txt` is the **runtime** what's-actually-loaded state. `maxim --llm <model>` is a one-shot **runtime swap** — it spawns/replaces the llama-cpp-server AND updates `active_llm_model.{role}.txt`, but does NOT update `config.json::llm.profile`. Per the C2 invariant, automatic runtime writes to declarative config files are FORBIDDEN; the CI grep allow-list in `.github/workflows/test.yml` blocks `set_field` calls from `lane_backends.py` for exactly this reason. The drift is by design — but it surfaces unhelpfully at sub-sim startup, where `_apply_lane_config_to_env` propagates `config.json::llm.profile` into `MAXIM_LLM_PROFILE`, then the singleton-check in `runtime/llm_server.py::check_existing_llm_server` sees configured=<stale> vs served=<new> and raises `RuntimeError`. **Symptom:** operator runs `maxim --llm mistral-small-24b` to swap the leader, then fires a sub-sim (cradle harness, simulation, etc.) and gets "configured 'qwen2.5-32b-instruct' but server is serving Mistral-...". **Resolution path the error message now spells out:** (a) adopt the served model via `maxim config set llm.profile <profile>`, (b) restart the runtime to match config.json, or (c) kill the existing server entirely. The architectural answer to "why not auto-update config.json from `maxim --llm`" is the same as the mesh.yml lesson: declarative config files must NEVER be mutated by runtime operations; operators write them explicitly. Regression guard: [src/maxim/runtime/llm_server.py::check_existing_llm_server](src/maxim/runtime/llm_server.py) — the error message includes the concrete `maxim config set llm.profile` command + the resolution branches.
