**[engineering] Don't run the benchmark harness on the same machine as the leader** (Exp 37 cradle smoke session, 2026-06-04): A four-hour debugging cascade traced back to running `scripts/benchmark_cross_session.py` on the leader's machine (a Mac Mini). The cascade: (1) sub-sims auto-detect role via `runtime/role.py`; rank 4 (`~/.cloudflared/config.yml` exists → leader) or rank 6 (`--language-model` flag → solo) both make the sub-sim try to spawn its OWN `llama_cpp.server`; (2) sub-sim's llama-cpp binds port 8100, collides with the leader's existing llama-cpp on the same port, one of them dies; (3) maxim's proxy on port 8099 loses its upstream and starts returning 502s; (4) the operator pkills the broken maxim to clean up, which also kills cloudflared (auto-spawned as maxim's child process), so the public tunnel goes down; (5) external requests get 530s from Cloudflare's edge because the tunnel origin is unreachable; (6) operator restarts maxim, tunnel comes back, next sub-sim restarts the same cascade. Visible symptom was "persistent 530s + sub-sim spawned a stray llama-cpp" — actual cause was the architectural mismatch. **Rule:** the harness was designed for a remote-LLM topology (originally Sonnet via API). Sub-sims send HTTPS to wherever their lane config points. Co-locating the LLM and the harness on one box requires the harness's child processes to bypass that machine's role-detection, which has no clean entry point. **Fix:** run the harness from a different machine. The laptop's `peer.yml` correctly identifies it as peer; sub-sims send HTTPS through the public tunnel to the Mac Mini leader; no port collision possible. **Diagnostic signature:** `cat <sandbox>/util/lane_decisions.jsonl` shows `tier_decisions.large.source: "tier_table"` instead of `"env"` AND `ps aux | grep llama_cpp` shows more than one llama-cpp process on the leader machine. **What does NOT work:** setting `MAXIM_ROLE=peer` + `MAXIM_LANE_LARGE_REMOTE_URL=http://127.0.0.1:8100/v1` in the harness shell — it papers over the immediate symptom but leaves the leader vulnerable to the next operator slip (any env-var leak, any new terminal, anything that re-introduces the role-detection-as-leader pathway). The architectural separation is the only stable answer. **Update (2026-06-05): both candidate hardenings landed, making the leader-local fire safe.** (1) **Singleton spawn guard** — `runtime/llm_server.py::check_existing_llm_server` probes the singleton port (via the canonical `_MaximPeerBackend.for_url(...).health_check()` entry point) BEFORE any spawn in `lane_backends._maybe_auto_spawn_server`: HTTP 200 + matching served model → reuse the existing server (skip spawn, no collision); HTTP 401 (auth-gated but alive) → reuse; connection-refused/timeout → spawn as before; HTTP 200 + DIFFERENT served model → raise `RuntimeError` (fail loud, don't silently serve the wrong model). This replaces the old kill-the-unowned-ghost behavior — a sub-sim on the leader now reuses the leader's live server instead of killing+respawning it. (2) **Harness preflight** — `scripts/benchmark_cross_session.py::assert_subsim_routed_not_local` reads the first sub-sim's `<data_home>/util/lane_decisions.jsonl` and raises `PreflightError` (exit 4) if `tier_decisions.large.source == "tier_table"` (the cascade signature). The reuse path is logged as `source="reused_server"` and env-routing as `source="env"` (both accepted) via `lane_backends._derive_decision_sources` → `decision_log.build_record(decision_sources=...)`; a fresh local spawn is `source="tier_table"` (rejected). With both in place the harness can fire from the leader using local Qwen14B with no tunnel involvement. Regression guard: [tests/unit/test_llm_server.py::TestCheckExistingLlmServer](tests/unit/test_llm_server.py) (spawn/reuse-200/reuse-401/fail-loud-wrong-model) + [tests/behavioral/test_exp37_harness_smoke.py::TestHarnessPreflight](tests/behavioral/test_exp37_harness_smoke.py) (rejects tier_table, accepts env/reused_server).
