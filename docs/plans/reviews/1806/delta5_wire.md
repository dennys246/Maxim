## 2. New findings

| W5-1 | **The daemon-name chain reads `--robot-name`/`MAXIM_ROBOT_NAME` for an entry selected by a new surface.** Case: `--device bob --unpinned` (or `MAXIM_DEVICE=bob`, or `embody bob --unpinned`), where `bob` is unpinned with no `host:` and no `config.robot_name`, and `MAXIM_ROBOT_NAME=alice` is set in the shell (a common legacy setup). Selection lands on `bob`, but chain step 3 gives `alice`, so the run dials `alice.local` and moves robot alice while the plan block and the log say `bob`. That contradicts §3.1's own "an environment variable outranked by a typed flag is ignored" (and `MAXIM_DEVICE` outranks `MAXIM_ROBOT_NAME`). The re-exec reproduces it faithfully, so it is consistent but wrong. Pinned entries are unaffected, because the daemon name never picks their address (§3.1, §4.2). The `--unpinned` grant covers "this entry is unpinned", not "dial a different robot's name". Fix (text): apply chain steps 2–3 only when that legacy source is the one that selected the run. For a new-surface selection, use `config.robot_name`, else refuse an mDNS dial for an unpinned entry with neither `host:` nor `config.robot_name` (the strict option), or else `reachy_mini`. Have the PR 2 writer always emit `config.robot_name`. Add a test row: `--device bob --unpinned` with `MAXIM_ROBOT_NAME=alice` | fail-open (narrow: an unpinned entry, an mDNS dial, a stray env var, `--unpinned` typed) | yes (daemon name, W3-5/W4-1) |

Fix (text): add `MAXIM_DEVICE` to the strict list in §3.1, to D13′ and to §3a's third exit bullet | fail-open by ambiguity (an unpinned run without the grant; a silent headless fallback) | yes (W3-3 strictness scoping) |
