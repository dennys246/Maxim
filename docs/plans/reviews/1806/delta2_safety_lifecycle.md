**Feasibility checks the round asked for:**
- **Step-3 placement** is feasible: in `controller.py::ReachyMiniController.connect`, the sequence is `ReachyMini(` → `_connect_released_media` → `_assert_auto_yaw_off` → `_probe_state_shape` → `_clear_latch_after_connect` → `CONNECTED`. Step 3 fits between the first two. Because it follows the assignment, D1 applies.
- **Stop latch from inside reconnect:** this is feasible. `RobotController.reconnect` calls `disconnect()`, which already runs `_stop(by_sleep=False)`, and a failed step 3 never reaches `_clear_latch_after_connect`. So the latch is set, but it is a *disconnect* latch. To get the sticky latch §4.5 intends, the identity path calls `stop_motion()` (`by_sleep=True`, which only a successful wake clears). It takes only `_abort_lock`, which `reconnect` does not hold, so there is no deadlock. That fits the latch owner rules (MP9: every transition goes under `_abort_lock`). A later wake could clear it, but the handle has been dropped, so motion stays refused.
- **`verified_identity()`:** see N3. It works because the default is `UNPINNED`, not because of anything in the subclass.

## Evidence

1. **Run modes.** `cli_parser.py` `--mode` `choices=["live", "train", "reflection", "sleep", "agentic", "exploration"]`. `modes/definitions.py::_LEGACY_NAME_MAP` maps `agentic/live/exploration/research` → `active` and `observe/reflection/sleep/train` → `passive`. `get_mode` checks `OPERATIONAL_MODES` before the map, which is why `passive/active/singularity` had to be refused (now done). `cli.py` `if mode == "agentic":` builds `ReachyEnv(data_dir=args.home_dir)` (observation-only per its docstring) and returns before `from maxim.embodied_runtime.selfy import Maxim`.
2. **Divergence media policy, and whether it is safe in the benign-race case.** `ReachyMini._configure_mediamanager` reads `self.client.get_status()` and, under `no_media`, calls `release_media()` unless the daemon reports `no_media`. The pre-release `daemon_status.media_released` is not kept on the handle, so the session daemon's pre-state cannot be recovered after `ReachyMini(` returns. If the controller re-acquires, it can steal a deliberate release from that daemon's owner. If it does nothing, it leaks a release that it may have caused. In the benign case (the IP moved to another robot between steps 1 and 2), the **pinned** robot was only REST-probed, so nothing is done to it, and on the other robot no joint moves (auto-yaw is a flag; media is a daemon pipeline). The other robot's camera clients fail until the media is re-acquired. A leak that can be undone with a known command, and that the log names, is the safer of the two errors. So v3's choice is safe for both robots' motion, and D8 makes the leak visible. D1 is about the controller's own flag, not the daemon.
3. **Latch.** `controller.py::_stop`, `stop_motion` (`by_sleep=True`), `_clear_latch_after_connect` (clears only a non-sleep latch), and `_clear_latch_after_wake`. `hardware/controller.py::RobotController.reconnect` runs `disconnect(); if self.connect(...)` with no `try`. `embodied_runtime/connection.py::ConnectionMixin._soft_reconnect` has only `try/finally` around `self._robot.reconnect(timeout=30.0, max_attempts=1)`, and calls `_degrade_capabilities()` only on a `False` return.
4. **Registry.** `registry.py::connect_robot_with_status` reuses only when `registration.controller.is_connected()`. Its `except BaseException` around `controller.connect` runs `controller.disconnect()`.
5. **Tunnel WebRTC host.** `reachy_mini.py::_configure_mediamanager` → `MediaManager(signalling_host=daemon_status.wlan_ip or "localhost", ...)`. Today's tunnel path sets `effective_mode = "localhost_only"`. v3 step 2 forces `network` against `127.0.0.1`, which works for the WS (`_connect_single(host=self.host)`) but leaves the WebRTC host at `wlan_ip`.
